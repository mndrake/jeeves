# M1 - Hear the browser

Status: code complete (2026-11-02); Mac tests pending. PRD: `docs/prd/01-audio-capture.md`.

M0 showed that a per-process tap captures a Meet call in Chrome with no gaps. But a tap
is fixed when it starts: if Chrome starts a new audio process, or the output device
changes, capture can silently stop. M1 makes capture survive a real call.

## What changed

| Piece | Where | What it does |
|---|---|---|
| `CaptureSession` | `Sources/AudioCapture/CaptureSession.swift` | Supervises the tap for a whole call (below) |
| `CapturePlanner`, `ExponentialBackoff`, `TimelineAligner` | `Sources/JeevesCore/CapturePlanning.swift` | The decisions, as pure logic with unit tests |
| `ProcessTap` | `Sources/AudioCapture/ProcessTap.swift` | Callback API, in-place retargeting, process restore, last-callback time |
| `spike-capture` | `Sources/SpikeCapture/main.swift` | Soak and event test tool with pass/fail checks |
| App and `spike-stt` | `App/Jeeves`, `Sources/SpikeSTT` | Now capture through `CaptureSession`; the app shows capture status |

`CaptureSession` handles:

- **The browser's processes change** (new tab, new call, helper restart). Core Audio's
  process list is watched, and polled once a second. If the browser's process set
  changes, the running tap is retargeted in place. If Core Audio refuses that, the tap
  is rebuilt, but only when a process it misses is actually playing, because each
  rebuild drops a moment of audio. Per-process taps also enable Core Audio's process
  restore, which may re-add restarted helpers by itself.
- **The output device changes** (AirPods connect or disconnect): the tap's aggregate
  device is rebuilt on the new default device.
- **IO stalls**: a tap delivers no IO callbacks until a tapped process first plays
  (after that, callbacks continue through pauses with silent buffers), so silence is a
  fault only while Core Audio reports the browser as playing. Then a tap
  with no audio yet gets 3 s and one that has delivered audio gets 1.5 s before it is
  rebuilt. Restarts that are restarted again before audio returns count as one outage.
- **Pauses** (video paused, nobody talking with the output stream closed): when audio
  resumes, up to 5 s of silence is inserted so speech timestamps stay aligned.
- **The browser quits**: capture pauses ("waiting for Chrome") and resumes when Chrome
  plays audio again. Jeeves can also be started before Chrome.
- **Rebuild failures** retry after 0.25 s, 0.5 s, 1 s, 2 s, then every 4 s.
- **Audio lost during a rebuild** is replaced with the same length of silence, up to
  5 s, so speech-engine timestamps stay aligned with real time.

Open question the tests answer: whether Core Audio accepts in-place retargeting
(`kAudioTapPropertyDescription`). The summary line `retarget` reports it.

## Tests

Install v0.1.0 or later (see `docs/M0.md`, "Download a build"), then run from the
unzipped `jeeves-spikes` folder. Use a Meet call in Chrome with someone talking (your
phone joined to the same meeting works).

| # | Test | How | Pass |
|---|---|---|---|
| 1 | 60-minute soak | `./spike-capture --minutes 60` during a call | All four summary checks PASS; no restarts while idle |
| 2 | Start before the call | Quit Chrome. Run `./spike-capture --minutes 3 --report-every 10`, then open Chrome and join | Status goes "waiting for Chrome" then "capturing" within about 2 s of call audio |
| 3 | AirPods | During a 5-minute run, connect AirPods, wait 30 s, disconnect | Each switch logs "output device changed", downtime under 2 s |
| 4 | Browser changes | During a 5-minute run, open a second Meet tab, reload the call tab, play a YouTube video | Audio continues (audible count keeps rising); note any restarts |
| 5 | Quit and reopen | During a 5-minute run, quit Chrome, wait 20 s, reopen and rejoin | "waiting for Chrome", then capturing again |
| 6 | Safari | `./spike-capture --browser safari --minutes 30` with Zoom or Meet in Safari | All checks PASS |
| 7 | App | Jeeves menu bar app during a call, with test 3 | Transcript continues across the device switch |

Tests 1-6 also work with a long YouTube talk instead of a call (Chrome taps hear any tab);
confirm with one short Meet run later, since call audio may use a different Chrome process.

For each run, paste the summary block (and any status lines) back for the record.

## Exit criteria (from PLAN.md and PRD 01)

- [ ] 60-minute Meet-in-Chrome call captured with no gaps, CPU under 5%, memory flat.
- [ ] 60-minute (or 30-minute) Zoom-web or Meet in Safari captured the same way.
- [ ] AirPods connect and disconnect recover within 2 s without user action.
- [ ] Opening tabs, a second call, or restarting the browser keeps capture working.

## Deferred

- Energy-based gating of silence before speech recognition (PRD 01 requirement 7). Tap
  CPU was 2% in M0; measure speech-recognition CPU in the soak before adding it, since
  skipping audio complicates the speech engine's timeline.
- Native Zoom and Teams apps (out of scope for v1).
